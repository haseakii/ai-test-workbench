# ADR-002：Java 业务单体与独立受控执行宿主

**状态：Java 分层仍为待评审提案；平台数据库改用 MySQL 8.4 LTS 的方向已获用户确认。**

提出日期：2026-10-26。修订依据：用户在讨论 PostgreSQL 与 MySQL 的取舍后，明确要求“好 你优化一下，直接在这个提交上更新”。本轮在 `a03e4e0` 的既有设计分支继续提交，不重写历史、不合并 main、不开展业务开发。

## 当前选择

用户偏好 Java 后端，现有产品需要在审批、预算、执行绑定与事件之间保持明确事务边界。建议以 JDK 21 / Spring Boot 构建模块化业务单体，**MySQL 8.4 LTS + InnoDB** 保存独立业务状态和事务 outbox；ACP 使用独立 Java Runner 承载受限 Agent 进程。平台仍通过同一 ExecutionProvider 接入外部总控，原有职责归属不变。

不采用全 Node 业务服务是维护偏好的取舍；不把每个模块拆成微服务，是为了避免首条闭环提前承担分布式事务与多组件运维。选择显式 JDBC/SQL 而非默认 ORM 聚合，便于审阅幂等、锁和额度预占。

## 数据库取舍与修订

原 `a03e4e0` 提案使用 PostgreSQL。当前采纳 MySQL 是为了贴合既有维护经验，并非 PostgreSQL 不适用，也不是 MySQL 具有尚未验证的性能优势。当前尚无业务数据库或迁移文件，因此本次属于设计改选，不是在线数据迁移。

首版只维护 MySQL 8.4 的平台存储方言和验收基线，不同时维护 PostgreSQL、MySQL 5.7、8.0 或 MariaDB 兼容。业务系统数据源仍按其实际类型独立接入；外部总控数据库保持独立，不因本决策迁移。

平台业务库与 Runner 接纳日志使用独立 database、账号及 Flyway 历史；可同实例部署，但不跨库查询、写入、外键或以跨库事务耦合两个进程。MySQL 的 database/schema 在本设计中指同一级库命名空间，不照搬 PostgreSQL 库内 schema 的权限模型。

MySQL 落地必须保留唯一未关闭 Binding、命令与事件去重、审批 CAS、总分账原子预占、出队重新准入、事务 outbox、原键核查和未知结果不重放。类型映射、生成列唯一约束、READ COMMITTED 短事务、UTC、迁移及竞争测试以[数据与事务](../development/DATA-AND-TRANSACTIONS.md)为准，不能仅替换驱动和名称。

## 代价与批准边界

需要编写 MySQL SQL、迁移及 Runner 接纳日志，并验证 JDK / Boot / Connector/J / Flyway / Java 协议库的实际兼容性。SDK 只减少协议工作，不提供业务审批、安全隔离或恰好执行一次。首次真实接入前按实际后端和协议版本验收；若必须增加薄协议桥，另记取舍，不扩张成第二套总控。

详细候选版本、目录与验收见[开发设计](../development/README.md)，本轮范围见[数据库决定与修订记录](../reviews/DATABASE-DECISION-20261026.md)。用户确认数据库方向不等于批准所有实现细节、冻结全部依赖或授权真实资源访问。没有创建服务工程、启动数据库或部署。ADR-001 继续有效。
