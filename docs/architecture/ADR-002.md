# ADR-002：技术栈与平台数据库

**状态：部分确认。** MySQL 8.4 LTS / InnoDB 已确认作为平台数据库方向；Java 架构与其他精确依赖仍是待验证的技术提案。

## 背景

平台需要在审批、额度预占、唯一执行绑定、命令幂等和事件恢复之间维持清晰的事务边界。维护成本也应尽量贴近现有 Java / MySQL 技术经验。

## 决策

采用以下候选组合：

- **后端**：JDK 21、Spring Boot 模块化单体、Spring MVC / Security。
- **平台数据库**：MySQL 8.4 LTS / InnoDB，首版只维护这一种平台数据库方言。
- **数据访问**：Spring JDBC / JdbcClient、显式 SQL、Flyway 迁移。
- **前端**：React / TypeScript，同源 REST 与 SSE。
- **执行**：独立 Java Runner；协议 SDK 只处理 ACP / MCP 通信，不代替平台的审批、幂等、额度和恢复逻辑。

平台业务库与 Runner 接纳日志使用独立 database、账号和迁移历史。可在同一 MySQL 实例部署，但不跨库查询、外键或共享事务。被排查业务系统的数据源和外部总控存储保持独立。

## 取舍

- 选择 Java 模块化单体，避免首版提前承担多服务的分布式事务与运维复杂度。
- 选择 MySQL 8.4，是为了贴合现有维护经验；不主张它相较 PostgreSQL 有未经验证的性能优势。
- 不同时维护 PostgreSQL / MySQL 双方言，也不承诺 MySQL 5.7、旧版 8.0 或 MariaDB 兼容。
- 选择显式 JDBC / SQL，是为了便于审查 CAS、唯一约束、额度预占与 outbox；不是因为 ORM 无法处理事务。

## 实施门槛

D0 必须验证 JDK、Spring Boot BOM、Connector/J、Flyway 与 ACP / MCP SDK 的实际兼容组合；D1 必须在真实 MySQL 8.4 / InnoDB 上测试迁移、锁、唯一约束、并发预占和崩溃恢复。精确补丁版本、容器摘要和连接参数在验证后冻结。

当前没有创建业务工程、数据库或迁移文件，也没有执行真实 Agent、业务数据访问或部署。数据库详细约束见[数据与事务设计](../development/DATA-AND-TRANSACTIONS.md)。
