# ADR-001｜独立业务平台与可插拔执行后端

> **状态：建议采纳，待顾帅审批。** 本文是架构决策提案，不代表已完成开发、已获批准或已接入真实资源。  
> 日期：2026-10-25｜适用：AI 测试协作平台｜关联：交互原型与系统设计 v0.2  
> 本次仅归档交付物、核查源码与协议并补充设计。未修改总控仓库，未新建业务仓库，未启动真实 Agent，未执行数据库操作。

## 01 / 决策摘要

**建议：独立建设 AI 测试协作平台，通过可插拔执行后端接入现有 multi-agent-control-plane，同时提供受控的 ACP 直连执行模式。复用总控的成熟能力，不把它设为平台唯一、不可替换的运行依赖。**

产品、数据、权限、发布生命周期独立；执行能力按接口组合。现有总控作为重点支持的执行后端，而不是必须继承的父系统。ACP 直连是后端执行节点充当 ACP Client，与已安装和授权的 Agent 通信，不是浏览器直接连接模型或开发机。

建议边界：

| 问题 | 推荐决策 |
| --- | --- |
| 是否在总控里直接堆测试业务模块？ | 不推荐。保持总控通用，业务平台独立。 |
| 是否另起一套完整多 Agent 总控？ | 不推荐。复用现有总控的调度、协作、工作区和审阅能力。 |
| 是否必须安装、启动总控才能使用平台？ | 目标上不必须。通过验收的基础流程应可在 ACP 直连模式独立运行。 |
| 是否所有流程都应能在两种模式间无损切换？ | 不要求。按能力门槛发布，复杂协作可以只支持总控后端。 |
| 是否现在就大规模拆包、重写引擎？ | 不做。先定义契约，评估窄范围复用，再实现两条最小真实链路。 |
| 两种模式何时算真正支持？ | 总控关闭时，直连模式仍能独立完成受控的基础排查；不能只有下拉框和占位接口。 |

这修正了此前“新业务层复用总控执行内核”的默认表述：**应复用能力，不应让业务模型、数据库和全部运行路径绑定总控的内部实现。** v0.2 原始文件保留不变，本文作为待审批补充，不擅自覆盖已交付基线。

## 02 / 为什么需要重新划清边界

测试平台的核心是一个业务问题从提出到验证解决的全过程：用户身份、系统环境、附件、业务口径、结果文件、审批责任、用户配额、问题重开和知识沉淀。

通用总控的核心是 Agent 如何被发现、分配任务、交换消息、持久化执行、恢复、隔离工作区并交付可审阅的产物。两者有交集，但不是同一产品。

测试人员需要的是“帮我核对这张报表”；总控需要的是“执行这个限定范围的任务并回传事实”。让它们通过接口合作，可以同时保留测试产品的完整性和总控的通用性。

另一个容易混淆的点：**接入其他厂商 Agent，并不是必须绕开总控的理由。**现有总控本身就是厂商中立的 ACP 总控，也支持普通成员直接执行，不要求每次都由 Boss 派工。[S1] 真正支持独立平台的理由是部署可选、业务权限独立、产品演进解耦和执行后端可替换。

## 04 / 四种方案对比

下表是本次设计判断，不是工时或成本测量。

| 方案 | 优势 | 主要代价 | 结论 |
| --- | --- | --- | --- |
| A. 在总控里直接增加测试模块 | 短期复用最多；单套数据和页面入口 | 多人身份与单机信任模型冲突；业务表、审批人和报表语义进入通用内核；升级与发布相互牵制 | 适合短期内部试验，不适合作为长期产品边界 |
| B. 独立业务平台，但执行必须经过总控 | 业务模型清晰；能快速复用执行能力 | 运行仍强依赖总控；不能称为独立运行；后续补直连时可能重构 | 可作为过渡，但不是最终目标 |
| C. 独立业务平台 + 总控后端 + 受控 ACP 直连 | 业务独立；复用复杂执行；基础能力可单独运行；后端可替换 | 要设计执行契约、能力协商、统一治理，并维护最小直连宿主 | **推荐** |
| D. 独立重写全部总控能力 | 理论上完全自主 | 重复建设 Boss 调度、消息、持久任务、工作区、恢复、审阅；维护两套相似引擎 | 不推荐 |

C 不是“完全不依赖任何总控代码”。直连宿主可以引用经过提取、版本化和依赖约束的公共运行库。**依赖一小段稳定库，与依赖整个总控服务及其私有数据库，是不同的耦合。**

## 05 / 推荐的系统结构

```text
测试工作台 / 平台管理后台
              │
              ▼
独立业务服务
身份与范围授权 · 问题会话 · 附件 · 业务流程
审批责任 · 预算账本 · 证据与结果 · 用户验收
              │
              ▼
执行后端契约 ExecutionProvider
              │
       ┌──────┴────────┐
       ▼               ▼
总控适配器          ACP 直连适配器
       │               │
multi-agent         受控 Agent Host
-control-plane      ACP Client / 进程与会话宿主
       │               │
任务 / Boss / 子任务    单 Agent 执行
       └──────┬────────┘
              ▼
受控工具与产物服务
代码快照 · 数据库查询/变更 · 日志 · 文件/表格
权限校验 · 脱敏 · 具体操作审批 · 审计
```

上图是目标逻辑关系，不表示所有代码必须拆成网络微服务。两种执行后端都只能获得其任务所需的资源引用和授权；敏感凭据不从浏览器下发，也不作为普通提示内容传给模型。

**业务平台是业务生命周期的拥有者；被选中的执行后端是这一次 Agent 执行的拥有者；工具服务是具体资源操作的执法点。**同一个执行单元不得有两个同时生效的调度者。

## 06 / 独立到什么程度，复用到什么程度

| 维度 | 推荐方式 | 不采用的方式 |
| --- | --- | --- |
| 产品 | 独立业务名称、导航、用户与发布节奏 | 把测试作为总控的一堆专用菜单 |
| 仓库 | 新业务仓库独立管理；建议私有，通用能力修复回到总控 | fork 整个总控后长期维护两个分叉 |
| API | 业务 API 与执行 API 分离，契约版本化 | 前端直接调用总控内部管理路由 |
| 数据 | 平台库保存业务真相；总控保存其运行真相，以外部引用关联 | 共用 SQLite 文件、跨库 JOIN、直接读写对方表 |
| 部署 | 独立进程和数据目录；可同机、同安装包启动 | 为独立产品立即引入微服务、Kubernetes 或多机集群 |
| 公共代码 | 窄范围复用 ACP 适配、内容规范化、模型确认、事件转换等 | 引入整个 runtime-composition、存储仓储和 UI 私有状态 |
| 多 Agent 协作 | 由总控后端提供；直连版先不复制 | 在业务平台实现第二套 Boss、通信路由、自动派工系统 |
| 数据库操作 | 统一工具服务与审批约束，两种后端一致 | 一个后端走审批，另一个直接读取开发者高权限连接 |

现有 Node/TypeScript/React 路径可继续作为默认候选，不因“独立系统”就重写 Java 或换数据库。用户业务代码仍按其实际 Java／MySQL 环境被读取与分析，平台自身技术栈是另一项决策。

### 公共库的提取顺序

先审查 acp-runtime 对 core、runner 的依赖，再划定最小接口。容易稳定的协议解析、模型配置确认、事件规范化可先复用；宿主注入权限决策、文件服务、事件存储和进程启动，不强制依赖总控数据库。

在发布成独立包之前，不把 private workspace 包描述成可直接安装的 SDK。可以先使用官方 SDK 构建薄适配器、复用经过审查的少量通用模块；不复制整套任务引擎作为“临时方案”。是否值得提包由依赖审查决定，不把抽象工作变成上线前的大工程。

## 07 / 业务流程与 Agent 任务不能互相抢所有权

平台需要自己的业务流程状态，因为“等待测试补条件”“等待审批”“用户确认解决”与 Agent 是否仍在运行不是同一个状态。但这不要求重写通用 Agent 调度器。

| 对象 / 行为 | 真相拥有者 | 另一方如何使用 |
| --- | --- | --- |
| 用户、角色、系统环境、可见性 | 业务平台 | 执行端接收限定范围的授权，不自建测试用户体系 |
| 问题会话与业务解决状态 | 业务平台 | Agent 回传输出，不自行把问题标为已解决 |
| 业务流程版本与节点顺序 | 业务平台 | 总控收到一个明确边界的执行任务，不重排外层审批和验收 |
| 总控内部 Agent 分工、任务树、原生执行尝试 | 总控 | 平台显示映射和事件投影，不复制写入总控状态 |
| ACP 直连进程、会话、单次调用 | Direct Agent Host | 平台记录执行回执；不在宿主中实现第二套业务工作流 |
| 预算和用户额度 | 业务平台账本 | 后端回报可获得的用量事实，子任务共享父预算 |
| 数据与代码操作实际结果 | 具体工具／执行服务 | 平台与总控消费可验证回执，不靠模型自述 |
| 审批人的业务授权决定 | 业务平台审批服务 | 原生执行策略仍可拒绝；外层批准不能绕过内层约束 |

建议模型：`Conversation → WorkflowRun → NodeRun → ExecutionBinding`。Binding 指向 `providerId + providerRunId`；总控模式另外保存外部 task/attempt 引用；直连模式保存本平台的调用 attempt 和 Agent session 引用。不要强迫所有后端复用总控 Task 的字段或状态枚举。

**两级重试规则：**由当前执行拥有者决定是否重试其执行尝试。平台不得在总控已经重试时另外提交重复任务。平台只在确认原执行结束、取消或未被接受后启动新的节点执行；未知结果进入核查状态。

## 08 / 统一的是执行契约，不是强迫所有后端讲同一种协议

总控后端有任务、子任务、审阅、审批和文件的原生语义；ACP 主要提供 Client 与 Agent 的交互。建议在两者上方定义平台自己的、范围很小的 ExecutionProvider 契约。

| 契约能力 | 语义要求 |
| --- | --- |
| `inspectCapabilities` | 读取实际后端、Agent、版本、模型、工具与恢复能力，带观察时间；未知不当作支持 |
| `validateBinding` | 校验节点所需能力、资源、数据发送策略、Skill/MCP 装配方案及预算 |
| `start` | 输入固定执行规格和幂等键；返回明确的接收回执及外部运行引用 |
| `getSnapshot` / `readEvents` | 查询运行事实和游标，断线重放可去重；不因读取而启动任务 |
| `submitInput` | 区分运行中排队补充、下一轮新提示、恢复旧会话；返回实际采纳语义 |
| `cancel` | 区分请求已提交、正在停止、停止已确认和结果未知 |
| `respondPermission` | 仅针对已识别的具体权限请求，绑定审批证据与有效期；不提供万能管理员批准 |
| `getArtifact` | 获取授权产物引用、大小和哈希；导入后成为受业务 ACL 控制的正式产物 |

以上是拟定契约，不是已经存在的接口。

`ExecutionSpec` 至少包含：契约版本、业务节点与幂等键、后端连接版本、执行目标、输入材料引用、目标系统环境、代码提交、执行身份、模型请求、Skill 版本、工具授权引用、预算预占号、期限与输出规范。

原始凭据不写入可见快照。`subjectContext` 由服务端认证生成，不能采信前端表单或提示词自报身份。运行事实另存模型确认值、实际用量、外部事件与产物哈希。

### 不建议首版只把总控包装成一个 ACP Agent

这样可以统一聊天入口，但难以充分表达总控的持久任务树、固定差异审阅、文件、审批和恢复诊断。最终往往又加入大量私有扩展。

总控 ACP 外观可以作为以后面对其他 ACP Client 的可选入口，但平台正式接入应优先使用范围受限、版本化的原生集成 API 或既有外部入口的演进版本。不要为协议统一丢掉已经有价值的执行语义。

## 09 / 两条执行路径的实际职责

### 路径 A：通过现有总控

适合需要多 Agent 协作、隔离工作区、代码修改审阅、复杂恢复与子任务管理的流程。也可以执行普通单 Agent 任务；复杂度不是强制路由规则。

平台先冻结业务上下文并预占预算，总控适配器再提交限定任务，记录外部 task 引用，持续读取事件与产物。总控自身处理原生分派和执行尝试；平台负责用户体验、外层审批责任、额度与验收。

当前外部入口已有项目授权和任务操作，不需要从零发明，但需要补足：业务用户身份映射与审计、受限审批桥接、二进制输入输出传输、业务资源与 Skill/MCP 装配、明确能力版本和预算上限传递。[S3]

不复制个人 owner 凭据给平台，不对外代理全部本机管理路由，不共享总控数据库。现有内部入口可作为第一轮适配基础，但不能直接宣称是已经稳定的多用户集成 API。

### 路径 B：后端 ACP 直连

受控节点上的 Agent Host 启动或连接一个已批准的 Agent。stdio 模式下由 Client 启动子进程，是官方文档定义的通信方式。[S8] 宿主完成初始化、能力检查、会话、模型确认、材料装配、事件接收、权限请求映射和取消。

首版目标是可靠的单 Agent 执行。不提供第二套 Boss、Agent 间任意通信或自动派工网络。业务流程可以顺序调用多个独立节点，但每个节点只由一个选定后端拥有。

直连并非零成本：仍需进程管理、队列限制、可追溯调用记录、断线识别、日志脱敏、产物收集与恢复策略。这些是最小运行宿主的职责，不应被隐去。

是否能原生恢复会话、读图、动态改模型、注入某种 MCP、上报费用，都要根据具体 Agent、协议版本、账户和实机验证决定。[S5–S7] 不支持时在发布或运行前拦截，或者采用经过批准且有明确提示的替代流程。

### 总控停机时的行为

已经绑定总控的运行标记“执行后端不可达”，保留外部引用并等待重连核对，不自动在直连后端重做。已经绑定直连的运行不因总控离线而失败。新增的基础任务可以使用已发布、已验收的直连策略；依赖总控多 Agent 能力的流程暂停并说明缺少的能力。

## 10 / 统一治理：不能出现直连绕过审批的后门

ACP 权限请求是 Agent 可发起的协议交互；看到工具事件，并不等于平台能拦截所有 Agent 自带的文件和终端操作。[S9] MCP 也只是提供工具调用接口，不自动实现业务系统的用户与环境授权。[S12]

**要控制资源，必须控制凭据、进程身份、可访问文件和网络，以及实际工具服务。**

建议两种执行后端使用相同的受控业务工具服务：真实只读账号、限定库表或业务查询服务、查询限时限量、导出 ACL、独立变更执行服务。写入以固定计划、环境、参数、影响对象和前置条件为依据执行。

Agent 不持有业务数据库的通用高权限凭据。需要原生终端或文件能力时，限定工作目录、服务身份、允许程序与外连范围；不把你的日常开发用户 HOME、全局配置和所有密钥原样提供给多人任务。

如果一个 Agent 无法落实要求的边界，应标记“协作式／边界未验证”，只允许符合其安全等级的场景。生产写入不因“已接入 ACP”而可用；必要时禁用其原生写工具，让变更全部经过受控执行服务。

工具网关对自己的凭据校验 audience、用途、环境、执行节点与有效期，不把收到的用户 token 原样透传给另一个服务。MCP 安全指南明确讨论了 token passthrough、会话劫持、本地服务器权限和范围最小化风险。[S13]

## 11 / 一个审批入口，多处执行校验

用户应在平台的审批中心处理业务审批，而不是在两个系统重复点击相同决定。但统一界面不能靠关闭总控原生策略来实现。

建立映射：`businessApprovalId → executionBindingId → providerPermissionRequestId → approvedOperationHash`。审批事件保留真实审批人、目标环境、动作哈希、批准范围、有效期和执行结果。

平台审批服务作业务授权决定；总控/Agent 的权限响应由适配器按具体语义提交；工具服务最终执行前再次验证。任何一层拒绝或状态不明都不得执行。已有 deny 策略不能被外层批准绕过。

当前总控外部入口不具备完整 operator 审批语义。[S3] 第一轮只读接入可以明确把尚未桥接的动作跳转到原生工作台，但“平台内完整审批”必须在受限桥接和端到端验收完成后才能宣称交付。不能用一个共享管理员 actor 字符串代替用户身份。

ACP 的短期权限请求与可能持续较久的人工业务审批也不能混为一谈。长时间等待应持久化计划和检查点；原请求过期后不得重放旧 permission option。恢复时重新验证动作与授权，必要时重新生成请求。

## 12 / 能力协商与版本，不以最低公分母设计产品

建议每个执行连接维护能力快照：版本、观察时间、认证状态、模型选项、图片输入、MCP 传输、Skill 加载机制、补充消息语义、会话恢复、持久事件、二进制产物、权限映射、用量上报、协作与工作区隔离等级。

每项区分 advertised、adapter_supported、verified、unknown、unsupported。真实验证还需绑定 Agent 版本与配置，变化后失效或重新校验。

| 流程需要 | 不满足时的处理 |
| --- | --- |
| 截图理解 | 使用已批准的多模态预处理节点，或禁止此绑定；明确原图和派生文字的区别 |
| 代码修改与差异审阅 | 只发布到具备已验收隔离与审阅能力的后端 |
| 多 Agent 协作 | 总控后端，或未来提供同等能力的其他编排后端；直连版不伪装支持 |
| 原会话恢复 | 能恢复则恢复，否则明确重建上下文，不声称原生缓存和隐藏状态被迁移 |
| 费用上报 | 显示真实值、估算或未知；不用上下文容量代替累计消费 |
| 业务写入 | 必须满足资源隔离、具体审批和执行回执门槛，否则阻断 |

ACP v1 的模型配置由 Agent 返回 configOptions；不能把平台维护的静态型号列表当作已生效设置。[S6] v2 在本次所查文档中仍是 Draft，须显式协商并单独验证，既有 v1 路径保留。[S10]

## 13 / Skill、MCP、环境与凭据的归属

**平台保存业务定义，执行适配器负责装配，资源服务负责实际授权。**

Skill 源码／说明、依赖、哈希、版本与发布记录属于平台业务配置。总控模式由适配器把固定版本的 Skill 包或内容引用交给受控工作区；直连模式由 Agent Host 按执行器支持的方式加载。官方 Skills 文档给出了文件读取、专用工具和内容注入等宿主集成方式，并非每个 Agent 都能使用同一安装目录。[S11]

Skill 文本被注入，不等于其中脚本已经可执行或其规则成为强制权限。工作流要求的 Skill 依赖缺失时应拒绝发布或执行；不能静默丢弃。

MCP 定义与工具白名单由平台按系统环境发布；凭据只由获准的工具服务／执行节点获得。平台与总控各自的配置不能同时成为同一连接的可写主数据。读取总控 Agent 目录可作为外部目录投影；要供直连模式独立使用，需要显式登记本地执行配置，而不是总控停机时临时猜测其内部路径。

平台登录、执行节点服务身份、模型 Provider 账号、MCP 服务凭据四种身份分开。复用同一 Agent 安装不代表共享同一活跃会话、同一可写配置或同一工作区；涉及全局配置修改时要隔离并发或加互斥锁。账户可用范围、组织数据发送策略和授权方式在接入审批时确认。

## 14 / 后端切换、上下文与产物

一个节点执行开始后固定 execution provider、连接 revision、Agent、工作区、模型请求、Skill、资源范围和预算。管理员修改默认后端只影响新的执行，不迁移已经运行的任务。

提交超时且不知道后端是否接受时，通过幂等键与查询核对，不立刻改投另一后端。外部写入结果未知时先核查实际结果；不得用“容灾切换”掩盖重复执行风险。

同一业务会话可以在下一轮改用其他后端。平台构造可携带上下文包：用户目标、已确认条件、证据与文件引用、代码版本、已执行操作、未决事项及有效授权。新执行器读取这一受控上下文，不保证获得旧模型的隐藏状态、会话缓存或未显式保存的推理内容。

正式附件、证据、产物由平台维护生命周期与 ACL；总控内部工件可保留来源引用，但平台需要授权导入或稳定的下载代理，以免总控清理后业务结果失效。文件以哈希和来源关联，不把大文件塞进事件或提示全文。

## 15 / 事件、预算与恢复的最小一致性规则

建议命令有稳定 idempotencyKey，事件有 providerEventId、业务关联和来源版本。平台持久化接收记录并去重；以外部运行快照校正断线、乱序和重复事件。不声称跨两个系统具有全局 exactly-once 执行保证。

平台保存业务运行状态；后端保存执行事实；页面是聚合投影。数据库或外部接口写入采用操作编号和可验证回执，未知结果单独处理，不自动重放。

预算由平台统一预占和结算。总控的根任务与子任务同属一个额度范围，不能把汇总用量与子任务用量重复相加。累计费用事件按来源和高水位计算增量，事件重放不再扣费。未上报保持未知；上下文占用不是消费总量。[S7]

凭据服务、工具服务和执行端都应识别暂停、撤销和预算停止信号。但已经发出的外部请求可能继续完成；界面区分“停止分派”“停止请求已发送”“已停止”和“结果待确认”。

## 16 / 部署建议：独立产品，不默认分布式重构

首版允许一台内网机器运行多个隔离进程：平台 Web/API、受控 Agent Host／工具服务，以及可选的总控服务。可以提供一个统一启动入口，但数据目录、身份和端口边界保持清晰。

延续已有 Windows 目录式部署思路即可，不因为采用适配器而强制引入 Docker、WSL、消息中间件、容器编排或多节点集群。需要数据库凭据隔离的服务不能仅靠“逻辑模块”名称宣称安全；隔离强度按实际风险与验证决定。

以后门户部署到其他机器或云端时，内网 Connector 通过认证通道接收限定任务；总控保留 loopback 接口，由同机连接器调用。远程通道、节点注册与租约属于后续明确实现，不把本地 stdio 或 localhost 地址当作已经可跨机器访问的接口。

业务数据与总控数据分别备份，各自维护 schema；跨服务引用和导入产物保留来源。开发环境、评审原型和正式实例分别保存，不使用现有个人总控数据目录作为多人生产实例。

## 17 / 对 v0.2 原型的调整清单

本轮只写调整规格，**没有修改原型或把界面升级为 v0.3**。

| 页面 / 对象 | 需要调整 | 原因 |
| --- | --- | --- |
| 全局导航 | “总控后台”改为“平台管理”；保留外部总控的明确入口 | 避免把业务平台后台误认为外部总控本体 |
| 新增“执行连接” | 新建总控连接或 ACP 直连；配置节点、认证引用、能力、验证时间、适用环境 | 执行后端是一等配置对象，不能和模型混成同一个下拉框 |
| ACP 与模型 | 展示执行连接 → Agent 实例 → 模型／参数预设的层级 | 同一 Agent 产品可以来自不同后端和账户 |
| 流程编辑 | 流程默认执行策略；AI 节点可覆盖；发布时能力校验；启动后固定 Binding | 管理员能选择执行方式，同时防止不支持的组合 |
| 审批详情 | 显示业务审批来源、原生请求映射、可执行范围和未支持桥接的原因 | 一个入口，不伪造万能审批 |
| 任务详情 | 显示执行拥有者、后端类型、外部 task/session、实际能力、模型确认与事件来源 | 排障时知道究竟卡在哪一层 |
| 系统环境 | 增加允许的执行连接、数据外发策略与隔离等级 | 换后端不意味着扩大数据权限 |
| Skill / MCP | 增加适配矩阵、装配方式和依赖校验；显示已传递／已读取／可执行区别 | 不是保存配置即生效 |
| 额度与审计 | 两种后端统一账本，显示用量来源、真实／估算／未知 | 不把切换后端变成绕过额度的方法 |
| 异常演示 | 后端离线、能力不符、审批桥接不可用、后端切换、结果未知 | 评审关键失效路径，不只演示顺利成功 |

普通测试人员仍然只需要选系统、环境和业务助手。执行连接与模型覆盖默认属于管理员或获授权高级用户，不把架构复杂度推给测试。

## 18 / 实施顺序与退出条件

### 阶段 0：先审批边界与最小能力

确认独立业务仓库、ExecutionProvider 契约、业务与执行状态归属、单一审批入口、统一资源策略，以及首版两条后端的验收范围。此阶段不启动大规模功能开发。

### 阶段 1：总控适配器打通真实只读链路

优先复用已有外部入口，完成一个系统环境的附件、代码／数据库只读排查、事件投影与结果交付。核清审批、二进制产物和执行上下文注入缺口，不能用界面按钮掩盖。

### 阶段 2：薄 ACP 直连宿主证明独立运行

选一个获准且已实机验证的 Agent，在总控关闭的条件下完成同类基础流程，复用同一业务授权、工具服务、结果格式和配额规则。验证补充、停止、失败恢复以及上下文重建的真实语义。

这不是等平台做完再补的遥远选项；**只有阶段 2 通过，才可以把首版宣传为“不依赖总控即可运行”。**在此之前应明确为“独立业务产品，当前执行仍依赖总控”。

### 阶段 3：补齐受控变更与复杂协作

完成平台内审批桥接、测试环境具体变更、结果核验，以及总控后端的多 Agent／工作区审阅流程。生产资源另行接入和验收。直连版不为了追平总控能力而复制多 Agent 引擎。

### 后续再做

更复杂的动态路由、跨后端并行、远程多节点、其他第三方编排平台、总控 ACP 外观。没有真实第二种需求时不做通用插件市场，不把所有潜在协议一次实现。

## 19 / 架构验收标准

| ID | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| ARCH-01 | 总控关闭，使用已发布的直连基础流程 | 能登录、上传、追问、执行授权查询并交付结果；不读总控私有数据库 |
| ARCH-02 | 相同基础问题分别走两个后端 | 业务权限、证据规范和配额一致；不要求答案文本完全相同 |
| ARCH-03 | 一方无法满足图片、恢复或审阅能力 | 发布／运行前拒绝，或显式采用已批准替代流程；不静默丢失能力 |
| ARCH-04 | 测试用户伪造 actor、环境或资源引用 | 服务端拒绝；不能借后端服务账户越权 |
| ARCH-05 | 通过直连尝试未经批准的数据库变更 | 实际工具层拒绝；不能绕过审批 |
| ARCH-06 | 相同权限动作同时出现在平台与总控 | 只有一个有效业务决定；原生限制仍执行；重复点击不重复变更 |
| ARCH-07 | 提交后响应丢失或事件重放 | 按幂等键核对；不新建第二份运行，不重复扣费 |
| ARCH-08 | 运行中修改默认后端或模型 | 已运行 Binding 不变；新选择只用于后续执行 |
| ARCH-09 | 写入断线、后端不可达 | 进入结果待确认；不自动切到另一后端再次执行 |
| ARCH-10 | 后端变化或会话不可恢复后继续追问 | 业务会话保留；以授权上下文重建并明确标识，不声称迁移缓存 |
| ARCH-11 | 二进制文件从总控输出 | 可授权导入、校验哈希、按业务 ACL 下载；不是只有模型报告的文件路径 |
| ARCH-12 | 全部子任务和累计费用事件回放 | 同一预算范围，去重结算，未知值不伪造为零 |
| ARCH-13 | Agent 可运行原生 shell | 实际验证文件／网络／凭据边界；不能仅因 worktree 或 MCP 白名单而判定安全 |
| ARCH-14 | 升级总控或 Agent | 契约与能力版本检查，失败可诊断；业务记录不随对方内部 schema 变化破坏 |

## 20 / 建议批准的架构范围

建议一次批准以下边界，而不是立即批准所有业务写入或正式部署：

1. 独立业务平台与独立仓库，现有总控继续通用发展。
2. ExecutionProvider 插拔契约，重点支持总控适配器和薄 ACP 直连宿主。
3. 业务流程／权限／额度／验收属于平台，底层执行尝试属于所选后端。
4. 两种后端使用同一受控资源和审批标准，禁止直连绕过治理。
5. 不共享数据库，不复制完整总控，不默认建设分布式系统。
6. 两条基础真实链路通过后才宣称独立运行；高级能力按后端真实能力开放。
7. 下一版原型按第 17 节调整；v0.2 原件保持为评审基线。

本提案不请求现在录入真实凭据、授予生产写权限或部署服务。数据库选型、具体机器容量、企业身份接入方式、数据保留周期和实际账号授权在后续实施方案中另行确定。
